## Практическая работа №2. Вариант 11

Инструмент анализа зависимостей Python-пакетов.

### Этап 1. Минимальный прототип

Реализовано CLI-приложение с аргументами:

- `--package` — имя анализируемого пакета (обязательный).
- `--repository` — URL репозитория или путь к тестовому файлу
  (обязательный).
- `--test-mode` — использовать локальный тестовый репозиторий.
- `--ascii-tree` — включить режим ASCII-дерева.

В первом этапе приложение выводит значения параметров.
Реализована проверка имени пакета, URL и тестового файла.

### Запуск

```bash
python src/main.py --package requests --repository https://pypi.org/pypi
```

На Windows также можно использовать:

```bat
run.bat --package requests --repository https://pypi.org/pypi
```

### Запуск тестов

```bash
python -m unittest discover -s tests -v
```

### Тестовый режим

```bash
python src/main.py --package A --repository tests/graph.txt --test-mode
```

### Требования

Python 3.10 или новее. Сторонние библиотеки не используются.

## Этап 2. Сбор данных

Реализовано получение прямых зависимостей Python-пакетов
из репозитория PyPI через JSON API.

Для получения данных используются стандартные библиотеки
Python: `urllib` и `json`. Менеджер пакетов pip и сторонние
библиотеки для получения зависимостей не используются.

### Основные функции

- `fetch_package_metadata()` — получает JSON-метаданные пакета
  с помощью HTTP-запроса.
- `get_direct_dependencies()` — извлекает записи прямых
  зависимостей из поля `requires_dist`.
- `show_dependencies()` — выводит найденные зависимости.

### Пример запуска

```bash
python -m src.main --package requests --repository https://pypi.org/pypi
```

Программа выводит список объявленных прямых зависимостей
пакета с ограничениями версий и условиями установки.

### Обработка ошибок

Предусмотрена обработка:
- отсутствующего пакета (HTTP 404);
- других ошибок HTTP;
- ошибок подключения к репозиторию;
- некорректных аргументов командной строки.

### Ограничения текущей реализации

Поддерживается JSON API PyPI. Произвольные репозитории,
не предоставляющие совместимый API, не поддерживаются.

Зависимости с маркерами `extra` пока выводятся вместе
с остальными записями. Обход транзитивных зависимостей
будет реализован на третьем этапе.


### Тестовый режим

## Этап 4. Порядок загрузки зависимостей

Реализован алгоритм топологической сортировки графа
зависимостей с использованием рекурсивного DFS.

Каждый пакет добавляется в результат после обработки
всех его зависимостей.

### Запуск с тестовым графом

```bash
python -m src.main --package A --repository tests/graph.txt --test-mode
```

Для тестового графа получен порядок:

```text
D -> B -> C -> A
```

### Запуск с PyPI

```bash
python -m src.main --package requests --repository https://pypi.org/pypi
```

### Сравнение с pip

Для сравнения использовалась команда:

```bash
python -m pip install --dry-run --ignore-installed requests
```

При проверке обнаружены одинаковые пакеты:

- requests
- charset_normalizer
- idna
- urllib3
- certifi

Наш алгоритм формирует топологический порядок,
при котором зависимости предшествуют пакету.

Вывод pip содержит выбранные версии дистрибутивов.
Порядок перечисления в строке Would install нельзя
считать гарантированным порядком установки.

Наш анализатор не выполняет разрешение версий,
не учитывает все маркеры окружения и пропускает
условные зависимости с символом `;`.

### Обработка циклов

При обнаружении циклической зависимости алгоритм
вызывает ValueError с указанием последовательности
пакетов, образующих цикл.

## Этап 5. Визуализация графа зависимостей

Реализована визуализация графа зависимостей Python-пакетов с помощью PlantUML.

Приложение строит граф зависимостей, сохраняет его описание в формате `.puml`, преобразует в PNG и открывает полученное изображение стандартным приложением Windows.

Дополнительно поддерживается текстовая визуализация в виде ASCII-дерева.

### Основные функции

- `generate_plantuml()` — создаёт описание вершин и связей графа на языке PlantUML.
- `save_plantuml()` — сохраняет описание графа в файл `.puml`.
- `render_png()` — запускает PlantUML через Java и создаёт PNG-изображение.
- `open_image()` — открывает готовое изображение.
- `generate_ascii_tree()` — формирует текстовое дерево зависимостей.
- `normalize_package_name()` — приводит имена Python-пакетов к единому виду.
- `get_plantuml_path()` — получает путь к PlantUML из переменной окружения.

### Требования для запуска

- Python 3.10 или новее.
- Java с возможностью запуска JAR-файлов.
- PlantUML в формате JAR.
- Поддерживаемая PlantUML установка Graphviz для построения диаграмм.
- Доступ к интернету при использовании репозитория PyPI.

Программа использует стандартную библиотеку Python для получения метаданных и построения графа. Готовые менеджеры пакетов и сторонние библиотеки для получения зависимостей внутри приложения не используются.

### Настройка PlantUML

PlantUML устанавливается отдельно от проекта. Путь к JAR-файлу передаётся через переменную окружения `PLANTUML_JAR`.

Пример настройки в PowerShell:

```powershell
$env:PLANTUML_JAR = "C:\Tools\PlantUML\plantuml.jar"
```

Для проверки установки:

```powershell
java -jar $env:PLANTUML_JAR -version
```


Построение графа пакета Requests:


В Windows приложение также запускается через `run.bat` с теми же аргументами.

### Результаты визуализации

Готовые файлы сохраняются в каталоге `output/`:

- `<package>.puml` — исходное описание диаграммы;
- `<package>.png` — готовое изображение.

Каталог `output/` исключён из Git с помощью `.gitignore`.

### Проверенные пакеты

**six.** Граф содержит одну вершину. Прямые зависимости отсутствуют.

**requests.** Граф содержит пакет Requests и четыре прямые зависимости: `charset-normalizer`, `idna`, `urllib3`, `certifi`.

**flask.** Граф содержит семь уникальных пакетов. Присутствуют транзитивные зависимости и общая зависимость `markupsafe`, на которую ссылаются несколько пакетов.

### Сравнение с pip

Для сравнения использовалась команда:

```powershell
python -m pip install --dry-run --ignore-installed flask
```

В проверенном запуске pip определил семь пакетов: Flask 3.1.3, Jinja2 3.1.6, MarkupSafe 3.0.4, Werkzeug 3.1.9, blinker 1.9.0, click 8.5.1, itsdangerous 2.2.0.

Набор пакетов совпал с результатом нашего анализатора после нормализации имён.

Различие заключается в том, что pip разрешает ограничения версий и учитывает условия установки, а разработанное приложение работает с метаданными пакетов и отображает зависимости без полноценного разрешения версий. Порядок пакетов в выводе `Would install` не считается фактическим порядком их установки.

Визуализация через PlantUML позволяет дополнительно увидеть направленные связи и общие транзитивные зависимости, которые не отображаются в виде графа командой `pip install --dry-run`.

### Ограничения

- Для сетевого режима используется JSON API PyPI.
- Зависимости с маркерами после символа `;` пропускаются.
- Полноценное разрешение версий не реализовано.
- Размер графа ограничен 50 пакетами.
- Открытие PNG рассчитано на Windows.
- Для создания PNG требуются Java и PlantUML.
